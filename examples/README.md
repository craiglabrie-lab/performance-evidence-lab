# Example test runs

Two synthetic load tests of the same invented checkout service, a week apart. The data is generated by [`tools/generate_synthetic.py`](../tools/generate_synthetic.py); nothing here comes from a real system.

| Test run | What is in the data | Expected result |
| --- | --- | --- |
| [01: load generator saturation](01-generator-saturation/) | LG2 runs with extended logging, saturates its own CPU, reports inflated response times, and loses Vusers to abort-on-error. A scheduled database batch job and a prompt-injection line in the generator log are there to mislead. | Test invalid: load profile not achieved. No capacity result. Test fix and retest. |
| [02: connection pool exhaustion](02-connection-pool/) | The retest. The load profile is achieved, then the third-party payment sandbox slows down. Checkout holds its DB connection during the payment call, both connection pools are exhausted, and every transaction slows. | Valid with limitations. SLA-1 and SLA-2 fail, SLA-3 passes. Suspected bottleneck in the application tier. |

## Each test run folder

| Path | Contents |
| --- | --- |
| `data/scenario.json` | Test objective, workload model, SLAs, environment, load generator settings, list of data files |
| `data/*.csv`, `data/*.log` | Transaction results, Vusers, load generator health, app server, database, network, and (run 02) outbound calls and APM traces |
| `facts.md`, `facts.json` | The computed results summary from `tools/analyze.py` |

Recorded agent runs (`run/` with every handoff file, and `TEST-SUMMARY.md`) will be added in the next stage. To run the analysis yourself with Claude Code:

```
/review-run examples/01-generator-saturation
```
